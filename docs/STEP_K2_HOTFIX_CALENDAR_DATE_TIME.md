# Step K2 hotfix — Calendar, date and time

Branch `luciev2_newteam`. This record covers `c6443a7` (device time and Enter to send), `7a71976` (shared calendar and campaign lookup), and `f516e05` (calendar grid styling). The comparison starts at `d3ad5c9`, the Step J baseline.

## Why the calendar looked saved while Neon was empty

In Step J, generating a campaign saved its response in chat history. Clicking **Save to Calendar** copied its posting slots into React state and then into local storage for that browser, account, and workspace. The calendar page read the same storage, so the posts appeared immediately and survived a reload. Neither action populated the marketing tables. Flask could retrieve the chat conversation but had no way to look up the schedule the user saw on screen.

With K2, generating a campaign still produces a draft in chat. **Confirm schedule** is the action that writes the plan to Neon. For example, confirming a three-post campaign creates one campaign, three content items linked to its source response, and three calendar entries linked to those items. Saving the same response again updates those identities. A standalone post uses a content item and a calendar entry. A manual reminder needs only a calendar entry.

## Changes to existing chat and generation code

| Existing code | What changed and why |
|---|---|
| [authenticatedApi.js](../client/src/lib/authenticatedApi.js) | The authenticated request wrapper reads the browser’s IANA timezone with `Intl.DateTimeFormat().resolvedOptions().timeZone` and sends it as `X-Device-Timezone` on chat and durable operation submissions. The device supplies the zone and Flask supplies the instant, so a Pacific user can get Tuesday evening even when UTC has advanced to Wednesday. |
| [app.py](../server/app.py), [chat_http.py](../server/services/chat_http.py), [generation_operations.py](../server/services/generation_operations.py) | The stateless chat route passes the header through its response wrapper. The durable operations route passes it through the orchestration layer to chat generation. Both entry points reach the same clock implementation. Flask also registers the new calendar API blueprint. |
| [generation.py](../server/services/generation.py), [generation_policy.py](../server/services/generation_policy.py), [requirements.txt](../server/requirements.txt) | Previously only the final campaign prompt received the server’s date through `date.today()`. Now `_clock_context` resolves the requested zone with `ZoneInfo` and supplies the weekday, date, time and UTC offset to ordinary replies, campaign clarification and final campaign generation. Missing or invalid zones produce a labeled UTC fallback. The clock goes in an uncached prompt block so each request gets a fresh time. The server declares `tzdata` for hosts that need timezone data. Campaign instructions now request explicit `YYYY-MM-DD` dates. |
| [generation.py](../server/services/generation.py) | A recognized question about an existing calendar or campaign triggers a workspace schedule lookup. The result goes into the prompt as untrusted record data. A lookup such as “What’s on my calendar this week?” can take the ordinary answer path even when its wording also matches campaign-generation rules. Creating a new campaign can still use the campaign output format. |
| [ChatPage.jsx](../client/src/pages/ChatPage.jsx) | Previously the textarea treated Enter as a newline. Plain Enter now calls the form’s `requestSubmit()`, which uses the same submit handler as clicking **Send**. Shift+Enter inserts a newline. Key repeats, empty input, blocked sends and Enter during input-method composition are guarded. The footer also tells users that calendar saves are shared with their workspace. |

## Changes to existing calendar UI code

| Existing code | What changed and why |
|---|---|
| [CalendarContext.jsx](../client/src/context/CalendarContext.jsx) | The provider previously seeded sample entries and implemented add, remove, clear and batch save as local array operations. It now loads a separate account/workspace snapshot, checks its revision through Flask, sends mutations to the API and refreshes after a successful write. Startup, opening Calendar and regaining window focus trigger revalidation. A failed refresh warns that cached entries may be stale. The separate cache key keeps a first empty database snapshot from erasing older local entries. |
| [CampaignResponse.jsx](../client/src/components/CampaignResponse.jsx) | The old save button derived dates from weekdays relative to the week of the click. Reopening an old plan could silently move it forward. The button now opens **Review workspace schedule** with editable dates and times. It prefers an existing saved slot, then an explicit generated ISO date, then the old weekday calculation as a visible suggestion. Confirming submits the source response ID, the slots and the revision seen at preview time. An unchanged saved slot retains its original instant and zone. |
| [PostsResponse.jsx](../client/src/components/PostsResponse.jsx), [ContentBriefCard.jsx](../client/src/components/ContentBriefCard.jsx) | A standalone post still offers its date/time picker and booked-slot hints. Its save callback now returns the workspace write result. The card waits for that result before dismissing the picker, so a failed save leaves the selection available. The source response ID and post index identify the individual post on subsequent saves. |
| [CalendarPage.jsx](../client/src/pages/CalendarPage.jsx) | Opening the page requests a refresh. Manual creation, deletion and bulk clear now await server confirmation. The clear dialog shows how many shared entries the selected range affects. The entry-detail dialog adds rescheduling and submits the revision seen when it opened. A separate import preview lets a writer review browser entries before sharing them. The grid container also dropped a redundant `bg-white` utility. Its `bg-slate-200` background shows through the one-pixel gaps between cells and resolves both Tailwind conflict warnings. |

## New API, storage and cache behavior

- **Calendar reads.** `GET /api/calendar` verifies JWT, current membership and `workspace:read`. The browser supplies its revision in `If-None-Match`. A match returns HTTP 304 after the revision check. A mismatch returns the entries, campaigns and revision from one repeatable-read snapshot. This avoids transferring a full schedule on every visit. [HTTP routes](../server/services/schedule_http.py) · [Repository](../server/repositories/schedule.py)
- **Calendar writes.** `POST /api/calendar` requires `chat:write` and `If-Match`. The transaction locks the member and workspace revision, verifies the source message through its workspace session, and commits the affected rows together. A stale revision returns HTTP 409 and the client refreshes for review. Deterministic IDs derived from workspace, source response and item position prevent duplicate campaign slots on repeat saves. Removing a slot preserves its content item, campaign and chat history. [Repository](../server/repositories/schedule.py)
- **Dates and legacy entries.** The client serializes a confirmed local time as an instant plus its scheduling timezone. The grid displays the event’s date in that zone. Import skips sample entries, preserves the original browser data, and links recognizable posts to an in-workspace source. Unlinked entries become manual items. Legacy times use the importing device’s zone because the old format lacked a dependable timezone. [Client date conversion](../client/src/lib/schedule.js) · [Calendar provider](../client/src/context/CalendarContext.jsx)
- **Chat reads.** A separate server-side cache is keyed by workspace, revision, date range and timezone. The lookup understands ISO dates and common relative windows such as “tomorrow” and “next week.” Its default window covers 30 days back through 90 days ahead. It supplies up to 40 entries and 20 recent campaign summaries, with truncation flags. A calendar lookup adds no extra model call. The UI handles schedule changes. [Schedule context](../server/services/schedule_context.py)
- **Database changes.** The migration adds `workspace_schedule_state` with one revision per workspace, plus `calendar_entry.display_data` for card details. Four row triggers advance the revision after inserts, updates or deletes on `campaign`, `campaign_persona`, `content_item` and `calendar_entry`. A multi-post save can advance it several times in one transaction. Clients compare revisions for equality. [Migration SQL](database/calendar_sync.sql) · [Deployment guide](database/CALENDAR_SYNC.md)
